# 0005: Auth is API keys with usage plans

Status: accepted on 2026-11-03.

## Context

The callers are machines: test suites, the library project, the other services, and an admin caller for the shipping simulation. There are no end users and no accounts. We need to tell kinds of callers apart and limit them, and we do not want to build or run an identity system for a demo.

## Options

- **API keys and usage plans** on REST APIs (ADR 0003). Identifies and throttles a caller, with nothing to build.
- **Cognito user pool with a JWT authorizer.** Real identities and scopes, but there are no users to sign in, and machine callers would need app clients and the client-credentials flow.
- **IAM authorization (SigV4).** Strong for service-to-service calls, but the library and test suites would have to sign requests with AWS credentials.
- **A Lambda authorizer with our own key store.** Flexible, but more code and cost than the problem needs.

## Decision

API keys with usage plans, three kinds of keys:

| Key        | Used by                             |
| ---------- | ----------------------------------- |
| `tests`    | Test suites and the library project |
| `services` | Service-to-service calls            |
| `admin`    | The shipping simulation endpoint    |

- The platform stack owns the three keys. Each service's usage plan accepts the ones it should and carries the throttle and quota limits, set low by default.
- Every route requires a key (`apiKeyRequired`), except `GET /v0/health` and `GET /v0/version`, so probes and test setup work without one. `GET /v0/health/ready` requires a key. The specs declare the `apiKey` scheme in the `x-api-key` header (`docs/spec-conventions.md`).
- Usage plans apply per API stage, not per route. Admin-only routes are enforced in the handler, which compares the caller's key id from the request context with the admin key id.
- CDK generates the key values. A key's value is not a CloudFormation output, so a script reads the values after deploy and stores them in Secrets Manager or an untracked local file. A value is never written into code, config, a template or the repo. Only the key ids are published to SSM.
- The gateway's own 403 (missing or invalid key) and 429 (throttled) responses are customized to the shared error shape.
- To rotate a key: create the new key, attach it to the usage plans, move the callers over, then delete the old one.

## Consequences

- No identity code to write, run or secure, and the library needs only an `x-api-key` header.
- A key is a shared secret. It carries no per-user identity, no scopes and no expiry, and anyone allowed to read API keys in API Gateway can read its value. That is acceptable for a demo and for machine callers, and it means we cannot test per-user authorization.
- `dev` stacks are destroyed after each run, so their keys change on every deploy and the retrieval script runs after every deploy.
- In production the choice would be Cognito (user pools with scopes on a JWT authorizer) for people and IAM authorization for service-to-service calls, or a Lambda authorizer in front of an external identity provider. Moving to either changes the security scheme in the specs, which is a breaking change under the versioning rule in ADR 0004. The README will say plainly that API keys are not a full authentication system.
