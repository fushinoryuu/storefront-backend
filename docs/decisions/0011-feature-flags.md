# 0011: Feature flags with LaunchDarkly

Status: accepted on 2026-11-11. One check is still open: the service connections of real traffic, after the first measurement (see Consequences). Amended on 2026-11-17: the Reader token check is recorded. Amended on 2026-11-21: the SDK is a `^` range, no longer an exact version. Amended on 2026-11-22: the bundle size, the cold start and the first service connections figure are measured. Amended on 2026-11-23: the project moved to Node.js 26 and the SDK was checked on it (see Consequences).

## Context

The Storefront shows feature flags for real. The first uses come later: switching on the `advanceShipment` simulation route (Phase 4) and the "customers unavailable" simulation (Phase 5). Services evaluate flags themselves, and the backend exposes no flag state through its API (decided on 2026-11-02), because that would show outside callers which flags are on. The per-run stacks of a pull request are destroyed after the run, so anything a flag client needs that must outlive them, such as an SDK key, cannot belong to those stacks.

## Options

- **AWS AppConfig.** Inside the account, with no new vendor and no new secret, and a Lambda extension that caches. It is a configuration service more than a flag product, and fewer people use it for flags.
- **LaunchDarkly.** The product most teams know for flags, and a free Developer plan. It adds a vendor, an SDK in every bundle, a key per environment, and plan limits.
- **Where the SDK keys live.** Secrets Manager costs $0.40 per secret per month. An SSM SecureString parameter in the standard tier costs nothing, but then there are two ways to read a secret. The `services` API key is already read from Secrets Manager (decision 0009).
- **Who creates the secrets.** By hand, which is easy to forget when the project is torn down. Or by a CDK stack that creates them empty, so the key value is never in a template and `cdk destroy` removes them.

## Decision

Use LaunchDarkly, on the free Developer plan, and not AppConfig. This project exists to show what teams use, and LaunchDarkly is that.

- **Plan limits.** Found on 2026-11-02: free, unlimited seats, 1 project, 3 environments, 5 service connections a month, 1,000 client-side monthly active users, and going over a limit warns and then makes the plan read-only. [The pricing page](https://launchdarkly.com/pricing) was read again on 2026-11-11 and gives the same project, environment, connection and user figures, but no longer says what happens past a limit. The account was checked on 2026-11-16, after it was created. The Developer plan card and the billing page show unlimited seats, 5 service connections and 1,000 client-side monthly active users free every month, and say "Never billed. Upgrade when you hit a limit." The account's Plan usage page (Settings) shows different limits: unlimited service connections and 25,000 client-side monthly active users, and it resets monthly on the first of the month UTC. The two differ because the account is in an intro period, which the owner says ends about 2026-11-25 (nine days after the check), and then it drops to the Developer limits. The design keeps to the Developer figures: 5 service connections and 1,000 users. Neither page shows the number of projects or environments, so those limits (1 and 3) rest on the 2026-11-02 reading and are unverified for this account. What happens at a limit, a warning and then read-only, is unverified too: the pages only say an upgrade is needed.
- **Environments.** One project with two environments: `dev`, shared by every pull request run (the runs are serialized), and `prod`. The third environment stays spare. A stage uses the SDK key of the environment with its own name.
- **SDK keys.** One secret per environment in Secrets Manager, about $0.80 a month for two. The `Secrets` stack (decision 0002) belongs to no stage, so one stack holds both secrets. It creates each one empty, with the name `storefront-<stage>-secrets-launchdarkly-sdk-key` (`docs/conventions.md`), and the owner puts the key in with `aws secretsmanager put-secret-value` (`docs/aws-setup.md`). No per-run stack owns the secret, and a test run does not destroy it. `cdk destroy` of the stack deletes both secrets, because the key can be copied again from LaunchDarkly. A service reads it once per execution environment with `createSecretProvider`, and its Lambda role gets read access when the first service uses a flag. A key is never in code, config, a template or a log.
- **Flag convention.** Every flag is a plain boolean with no targeting rules or percentage rollouts. ON serves `true` and OFF serves `false`, so a flag's state is the `on` value of its environment. A test that changes a flag is optional and puts the old value back afterwards.
- **The code never depends on LaunchDarkly.** `packages/shared` has a registry with the key, the default and the description of every flag the code knows, and `createFlagClient` takes only keys from it, so an unknown key fails typecheck. A flag is answered with its default when the SDK key cannot be read, the SDK is not ready within a configured timeout, it gives up, or an evaluation fails. The client reports each fallback so the service can log it. A simulation defaults to off.
- **One SDK, one context.** The SDK is created on the first evaluation and reused. Every evaluation uses one context per service (`kind: service`, `key: <service name>`), which also keeps the number of contexts at three. The service name is the SDK app id, so the usage page can show which service uses what. Evaluation events are not sent, because nothing here reads them and a Lambda function freezes between calls.
- **Reading a flag from outside.** The library and the tests read the state of a flag from the LaunchDarkly REST API with a personal token that has the built-in Reader role. Reader is enough: on 2026-11-17 a Reader token read a flag with `GET /api/v2/flags/<project key>/<flag key>`. Whether REST API calls count as a service connection is unverified.

## Consequences

- No service can fail because LaunchDarkly is down or out of plan. The cost is that a flag then silently has its default, so `onFallback` should be logged. While LaunchDarkly is down, every evaluation can wait up to the timeout, so a service picks a short one.
- Service connections for Lambda are counted by connection time, not by instance. [The documentation](https://launchdarkly.com/docs/home/account/service-connections) says a function that runs under a minute is sampled once a minute, and each sample counts as 1/43,800 of a connection, and that pre-production environments count. The earlier note in the Phase 1 doc that this is not documented is out of date. Measured on 2026-11-22: after the hello service had read a flag in `dev` about 9 times that day (most of them on a cold start), the usage page showed `0.001` in "Monthly accumulated usage as of today", up from `0`. That is 0.02% of the 5 service connections a month, so there is no reason to change the client. The figure is rounded to three decimals, so it cannot be compared exactly with the documented rule, and it may update late. It is one day of a few calls, so read the page again after a phase has run its tests against `dev`, and record the number here. If it is too high then, switch the SDK to polling or let fewer services read flags directly.
- A new SDK key takes effect only in execution environments that start after the change.
- The SDK (`@launchdarkly/node-server-sdk`, a `^` range with the version fixed by the lockfile, Apache-2.0) adds to the bundle of every function that reads a flag. Its README supports Node.js 16 and above, and the unit tests here run on 26 (24 when the bundle below was measured on 2026-11-22). Measured on `dev` on 2026-11-22, with the bundle built as `ServiceFunction` builds it (esbuild, the AWS SDK left out): 654,445 bytes with the SDK, the logger and the secrets provider, against 79,885 bytes with only the logger and the correlation id, so the SDK adds about 575 kB. Init duration of a cold start at 256 MB, from 6 forced cold starts of each: 278 to 402 ms with the SDK (median about 300 ms) against 112 to 129 ms without (median about 120 ms), about 180 ms more. The first flag evaluation of a cold start then takes 0.8 to 1.1 seconds inside the handler, for the secret read and the connection. A function that evaluates a flag therefore starts slower, which is one more reason to keep the flag timeout short (3 seconds in the hello service). `docs/platform.md` has the table.
- Checked on 2026-11-23 for the move to Node.js 26 (`nodejs26.x`, offered by Lambda since 2026-11-20), with SDK 9.16.6: the README still says Node.js 16 or later, and the SDK has no `engines` field. The GitHub workflow of the SDK (`server-node.yml`) runs its tests on Node.js 22 and 24 only, so upstream does not test 26. In this repository the flag tests load the real SDK and evaluate flags with its `TestData` source, and they pass on Node.js 26. Not checked on 26: a connection to LaunchDarkly from a deployed function, which was measured on Node.js 24 only. Check that on the first deploy of a service that reads a flag.
- Some steps stay manual: the account, the project, the two environments, the two flags, the Reader token, and putting the two key values into the secrets. A deleted secret is recoverable for a recovery window, and is not billed while it waits (AWS documents this).
- Source: [LaunchDarkly service connections](https://launchdarkly.com/docs/home/account/service-connections).
